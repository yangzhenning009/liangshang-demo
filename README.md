# 梁山集团企业领域模型 Demo

本地主数据演示，覆盖法人、公司（含分公司）、自然人、员工、部门、来源材料、供应商、项目、合同、工时、费用、报销、发票和收付款。公司下面可以维护登记版本、银行账户、股东明细和公司版本；部门可以维护服务公司和部门版本。员工详情页维护雇佣、部门任职和汇报线。供应商档案维护联系人、供货类别、资质和版本。项目维护成员、预算版本、交付公司、支持部门和管理版本。合同维护条款版本、品项、变更、阶段、交付项、附加签署方、开票计划、收付款计划、交付和验收，以及项目与合同的关联。员工按天填报工时，行政上级在工作日有效时才能批准或驳回。费用只记一次，并可以分到项目。员工垫付报销批准后形成应付。

模型依据 `docs/` 里的领域说明和逻辑 Schema。数据库只保存主键、基本类型、`NOT NULL` 和普通索引。关联是普通的可空 `Long`，没有外键、`CHECK` 或业务唯一约束。公司类型、一对一、股东单选、任职期间、汇报无环、供应商规则、项目规则、合同规则、履约数量、工时资格和成本率期间由应用层校验。

这一版对应工作包 WP-01 至 WP-09。发票和完整收付页面还没有单独入口。报销批准会生成最小应付，并可以按应付付款。

## 环境

- Java 21
- Maven 3.8+
- Spring Boot 4.1
- 本机 SQLite 文件 `./data/liangshan.db`

## 数据库

升级之后必须先删除 `data/liangshan.db`，再启动。SQLite 的 `ddl-auto=update` 只加列，不会删掉或收窄旧列；留着旧文件会和当前实体不一致。

`src/main/resources/application.yml` 使用 `spring.jpa.hibernate.ddl-auto=update`。同一版本内重启会保留 `./data/liangshan.db`。元数据按表单独读取，避免 SQLite 在表变多后拒绝 Hibernate 的合并查询。旧库 `work_log` 上若仍有人工成本快照列，启动时会抄到 `cost_occurrence`，页面之后只读成本行。跨版本升级不要依赖这次抄写，按上面的要求先删库。

测试使用另一份库 `target/test-liangshan.db`，并用 `ddl-auto=create`。

```bash
mvn test
```

## 应用层约定

- 未知的号码、金额和可选关联保存为 `NULL`，不写空字符串。
- `company_type=company` 必须有 `legal_person_id`，`head_company_id` 留空，并填写公司形式。同一法人只能对应一家公司。
- `company_type=branch` 必须有指向公司类型记录的 `head_company_id`，不能指向自己。法人、公司形式、注册资本和股东留空。
- 股东在公司、法人、自然人中恰好选一个。公司股东必须是公司类型。持股比例按 0 到 1 保存。
- 当前未结束的 `company_registration` 会在同一事务写回公司上的证照、税号、注册资本和营业期限。跨日修改登记或公司核心资料时保留旧版本。
- 员工通过 `person_id` 与自然人一对一。部门编号在所属公司内不重复，行政上级不能成环。
- 雇佣的用人对象在公司和法人中恰好选一个。用工编号在该用人对象内不重复。任职期间落在雇佣期内，汇报期间同时落在双方任职期内。行政汇报链不能成环，也不能指向同一条任职。
- 供应商确认时，`company_id`、`legal_person_id`、`person_id` 恰好一个。编号在采购公司内不重复。同一采购公司与同一供货对象只留一份档案，公司供应商不能再以其对应法人建档。
- 供应商被合同、费用或应付引用后，采购公司和供货对象不能更换，档案也不能删除。引用由 `SupplierUsage` 声明；`ContractSupplierUsage` 同时看合同头和历史条款版本上的 `supplier_id`。仅有版本或资质不会锁定身份。建档写入版本 1，状态或条件变化在同一事务写版本。
- 有效联系人至少有电话或邮箱。同一角色在重叠期间最多一个有效主联系人。资质长期有效时到期日留空；到期日未知时 `has_no_expiry` 为假且到期日留空。
- 项目客户在公司、法人、自然人中最多选一个。牵头部门属于项目管理公司。成员的雇佣、任职必须属于该员工，成员期间落在对应有效期内。
- 预算人工和非人工金额未知时保存为 `NULL`，不用零代替。两项都已知时总额为两者之和。当前已批准且期间覆盖今天的预算版本写回 `approved_budget_version_id`。
- 项目建档写入管理版本。客户、管理公司、负责人、类型、范围、名称或计划日期变化时，在同一事务维护版本。交付公司和支持部门各自保留期间。项目详情可以关联合同。
- 合同买方、卖方各自恰好一个。采购合同保存 `procurement_company_id` 与 `supplier_id`，并核对买方公司、卖方对象与供应商档案一致。阶段编号和序号在合同内不重复。
- 建档写入条款版本 1。签约对象、供应商、总价或合同期间若跨日变更，须登记变更；变更关闭当前版本并写入新版本，同时复制品项条款、阶段条款和交付项。原版本的金额与签约方不改写。同一天内的条款修改直接更新当前未结束版本。
- 品项与合同金额在不含税、税额、含税都已知时核对含税等于不含税加税额。未知金额保持 `NULL`。单价是不含税单价，不按数量乘单价回填约定金额。
- 条款版本用 `agreed_valid_from` / `agreed_valid_to` 保存约定的合同生效与结束日，用 `valid_from` / `valid_to` 保存该版本自身的有效期间。
- 开票计划和收付款计划分开保存。指定日期须填计划日期；相对触发须填日历天数和阶段，不在这里推算实际到期日。被替代的计划保留，并在应用层避免序号重复和替代成环。
- 一次交付的提交方恰好一个，交付项属于所引用的阶段条款，且项目已关联该合同。累计交付只计首次提交；重提数量不能超过原交付尚未通过的数量。
- 验收数量等于通过加不通过。复验只确认尚未通过的部分，原验收明细上的通过数量保持不变。累计不通过是仍未通过的数量。累计通过不得超过已交付数量，也不得超过该阶段交付项编号的约定数量。已撤回的交付和已撤销的验收不计入累计。
- 只有项目成员可以填工时，且成员、雇佣和任职期间都要盖住工作日。任职必须属于该员工和该雇佣。所选阶段的合同必须已关联到该项目。工时须大于 0。
- 草稿可改。提交后进入待审，待审不能改。只有填报人在工作日有效的行政汇报上级可以批准或驳回。批准记下审批人和时间，并按当时覆盖该雇佣、已批准的标准成本率生成一笔人工成本，把成本率主键、单价和金额记在 `cost_occurrence` 上。之后改单价或另记版本，不回写这笔金额。驳回必须填写原因，不记成本。不能审批自己的工时。职能汇报不能审批工时。
- 已通过的工时不能直接改。更正是新的一条，指向原记录；新记录批准后，原记录和原人工成本变为已被替代。工资成本率只保存，不自动套到工时上。同一雇佣和口径的有效期间不能重叠；已被人工成本引用的单价不能就地改。
- 费用的承担对象在公司和法人中恰好一个。填写供应商档案时，供货对象必须与档案一致。有效分配合计须等于成本金额。同一工资来源不重复导入。工时人工成本只能分配到该工时的项目和阶段。
- 报销类型包括项目费用和体检费用。只有已批准且有员工垫付的费用可以报销，申请金额不超过垫付，同一垫付不能重复进入未驳回的报销单。只有报销人在提交日有效的行政上级可以批准或驳回，职能汇报不能审批。批准后生成应付，债权人是报销员工对应的自然人，债务公司是承担报销的公司。按应付付款只核销这笔应付，不另记成本。
- 费用或应付引用供应商档案后，采购公司和供货对象不能更换，档案也不能删除。
- 发票行可以按含税口径覆盖应收或应付，覆盖不增加本金。未结等于调整后本金减去已确认核销，再加上已确认撤销。退款是一笔方向相反的收付款，并撤销原核销。第三人付款时，实际付款人与被代付对象分开记录，且须有代付依据。费用匹配发票行时，合计不得超过该行含税金额。
- 从收付款计划或开票计划确认结算项时，相对触发按验收日、签约日或开票日加日历天数写入到期日。人工确认不解析说明文字。同一收付款计划只确认一次结算项。
